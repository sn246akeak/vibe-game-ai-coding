# Progress and Resumption

For v1, `workflow.json` is authoritative and `STATUS.md` is generated by `workflow.py`. Do not manually maintain two competing progress boards. See `workflow-runtime.md` for commands and the legacy migration boundary.

Track one active module and an ordered fixed-version queue. States are intake_needed, designing, ready_to_build, implementing, verifying, needs_user_review, accepted and deferred. Blockers stay in the current state with a note naming the missing input and next action. Do not label unstarted or blocked work accepted.

Use short updates in the user's working language:

```text
当前模块：卡牌最小闭环 / verifying
进度：已验收 4，明确延期 0，总计 10
本轮完成：接入抽牌、出牌、弃牌；检查报告已落盘
下一步：请体验指定场景，确认验收或提出修改
```

The generated board includes context, queue, active delegation, history and evidence. Keep detailed current contracts, frozen scope and deferred ideas in linked project documents. Use `workflow.py note MODULE --note "needed input / blocker / next action"` for useful resumable notes without changing state.

On resume, inspect current state, active spec and actual source changes, latest evidence and any delegation. Validate snapshots before continuing implementation. A prior successful test is not proof after code changes. Do not restart accepted modules or skip their successors.

Log productive instructions and actual decisions, changed IDs/files, checks, limitations and reusable commands. Do not reproduce emotional conversation, secrets or invented quotations. Exported status is an evidence index; a richer reusable SOP should explain the choices and scripts actually exercised.
